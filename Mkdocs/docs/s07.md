# S07 / S07b · Identidad y autorización

Keycloak emite tokens RS256. Gateway y cada microservicio son Resource Servers y verifican JWK y emisor. `realm_access.roles` se convierte en autoridades de Spring. CLIENTE solo accede a sus datos; ADMIN administra y simula pagos; AGENTE mantiene catálogo y agenda según las rutas permitidas.

## Flujo web

El cliente público `casa-o-nada-web` usa Code + PKCE S256, redirect exacto `localhost:4300`, sin password grants. El cliente separado `casa-o-nada-tests` habilita password grant únicamente para scripts locales de laboratorio. No es el flujo del navegador.

## Identificadores

El `sub` de Keycloak es String; `cliente_id` es un atributo que enlaza con el ID numérico del dominio existente. El servidor obtiene ese vínculo del JWT firmado. Se mantiene este modelo para preservar los datos del proyecto, en vez de convertir todas las claves de negocio a UUID.

## JWT propio y reemplazo

El material S07 estudia un emisor JWT propio. Esta base del equipo ya utiliza Keycloak y no incluye un servicio de autenticación propio: no se presenta como implementado. El contrato que permite sustituir un emisor consiste en conservar roles, sujeto e identidad de negocio y cambiar issuer/JWK, con pruebas de permisos. Keycloak es el proveedor final requerido para S11.

## Pruebas

`test-stability.ps1` comprueba 401, 403, pertenencia y rechazo de monto adulterado. `test-distributed-security.ps1` comprueba acceso directo a los nueve microservicios, separado del Gateway. El catálogo GET es público; se usa una ruta protegida para demostrar 401.
